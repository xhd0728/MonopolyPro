# 服务端 LLM 机器人

规则引擎始终负责掷骰、费用、归属、合法性和胜负。LLM 只从服务端生成并验证的候选动作中选择序号。API 请求位于 `apps/server/src/ai.ts`，规则引擎没有网络依赖。

## 本地配置

Node.js 24 启动时自动读取根目录 `.env`（测试服务不读取）；已有进程环境变量优先。此次只将本地 KatanPro 的 `CATAN_AI_*` API 配置映射为 `MONOPOLY_AI_*`，保存在权限 600 的忽略文件 `.env`。没有复制卡坦岛的服务器端口或其他设置。

```dotenv
MONOPOLY_AI_ENABLED=true
MONOPOLY_AI_API_MODE=chat
MONOPOLY_AI_BASE_URL=https://your-provider.example/v1
MONOPOLY_AI_MODEL=your-model
MONOPOLY_AI_KEY=your-key
MONOPOLY_AI_TIMEOUT_MS=20000
MONOPOLY_AI_MAX_CONCURRENT=8
MONOPOLY_AI_MAX_STEPS=4
MONOPOLY_AI_PROTOCOL=tools
```

支持 `chat`（Chat Completions）、`responses` 和 `anthropic` 三种协议。URL 可为基础路径或对应完整接口路径。关闭 `MONOPOLY_AI_ENABLED` 后不请求模型。

公网 systemd 部署时，将这些字段加入 `/etc/monopolypro.env` 并限制权限，然后重启服务。密钥不会通过 API、房间状态或前端设置返回。部署包和 Git 不包含本机 `.env`。

## 行为与连续性

房主可选择规则机器人或 LLM 机器人；未配置模型时只允许添加规则机器人。旧存档没有 `botMode` 的席位继续使用规则策略。显式 LLM 席位在模型配置撤掉时回退到规则策略；真人断线托管继续使用本地规则策略。

机器人每次决策最多两分钟：`MONOPOLY_AI_TIMEOUT_MS` 是单次请求上限，最大 120000（默认 20000），服务端另有两分钟总上限，到时中止请求并由规则机器人接手。真人玩家默认不限时，房主可以在房间里设置 60 / 120 / 300 秒的操作时限。

LLM 获得该机器人自己的手牌和公开局面，对手手牌、预设骰子、席位恢复凭证和密码不会进入请求。请求只允许选择候选序号；超时、HTTP 失败、过大/格式错误的响应或非法序号会回退到规则机器人。并发数有上限，拥堵时也由规则机器人继续。不会无限重试或因模型不可用卡住对局。

每个异步任务绑定房间、对局 ID、状态版本、席位与控制 epoch。返回时重新核对，过时结果废弃；最终动作再次由引擎校验，快照和事件事务落盘后才发布。服务关闭时取消未完成请求。

前端显示模型是否配置、机器人模式、思考/回退状态。公开的只有工具标签和经过过滤的简短理由，不发布模型原始输出或内部推理。

## 决策框架（2026-10-13 重做）

### 为什么之前经常是「规则机器人接管」

实测（本机 `qwen3.8-flash-next`）：单独调用模型 47 次决策没有一次回退；但 6 个房间同时各有 2 个 LLM 机器人时，99 次需要说明的动作里有 41 次由规则机器人直接代打。主因是服务端最多同时 4 个模型请求，满了就立刻交给规则机器人；以前没人的房间不会关闭，留下的机器人一直占着名额。另外 429 / 5xx 不重试，每次请求还带上整份客户端局面（上万 token），也拖慢了速度。

### 现在的设计

参考 Codex CLI、DeepSeek Harness 和 Anthropic 关于工具设计的建议：

- **每次决策一个新上下文**：固定的系统提示（规则要点、风格、协议）加一份紧凑局面（`apps/server/src/ai-observe.ts`：自己的现金、手牌和天赋，对手的公开资产，所有地产的主人、等级、租金，当前局面和最近 6 条事件），只有几百 token。
- **原生工具调用**：只读工具 `look_ahead`、`square`、`player`、`preview`、`advice`，以及唯一的决定工具 `act`。查询次数用完后强制调用 `act`（`tool_choice`）。Chat Completions、Responses、Anthropic 三种接口都用各自的原生工具格式；接口拒绝工具定义时自动永久切换到纯 JSON 协议（`MONOPOLY_AI_PROTOCOL=json` 也可以直接指定）。
- **更多动作**：`act` 可以选候选编号，也可以给出自定义动作——主动发起交易（任意现金和地块）、还价、任意竞拍出价、存取任意金额。规则机器人自己想到的动作（例如收购凑组所缺的地块）也会放进候选。
- **校验与自我纠正**：每个动作先在副本上按真实规则试执行；不合法时把引擎给出的原因作为工具结果返回，模型据此修正，最多两次。
- **回合计划**：经营阶段 `act` 可以带 `then`，一次排好后续的升级和结束回合；之后每一步执行前重新校验，不合适就重新询问模型。实测约一半的经营决策因此少发一次请求。
- **容错**：429、5xx、网络错误和单次请求超时在时间预算内重试一次；文本里的 `<tool_call>`、JSON 或候选编号也能识别（Qwen 有时把工具调用写进正文）。
- **排队而不是放弃**：模型名额满时，机器人最多排队 20 秒（右下角显示「排队中」），之后才由规则机器人代打。默认并发上限提高到 8（`MONOPOLY_AI_MAX_CONCURRENT`）。
- **兜底顺序**：原生工具调用 → 文本识别 → 纠正提示 → 规则机器人（附带它的理由）→ 超时默认动作。每次回退都会在动态里标注原因。

### 难度

房主在房间里给每个机器人选「简单 / 普通 / 困难」，规则机器人和 LLM 机器人都适用。

| 难度 | 规则机器人                                                      | LLM 机器人                                                                |
| ---- | --------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 简单 | 凭感觉买地，很少建房，不主动交易，交易只看标价                  | 不查询，只能选候选，温度高，约 25 秒预算                                  |
| 普通 | 启发式策略                                                      | 最多 2 次查询（前方风险、地块、规则建议），可自定义动作和计划，约 50 秒   |
| 困难 | 积极建房到 3 级、凑组报价更频繁、绝不廉价卖出对手所缺的最后一块 | 最多 4 次查询（另含玩家资产与预演），候选里标出规则机器人的推荐，约 90 秒 |

三档规则机器人同桌 300 局：简单 21%、普通 26%、困难 52%（`scripts/levels.ts`）。每档都受两分钟总上限约束。

### 实测

改造后用本机模型：困难难度单机器人 120 秒内 40 次决策全部由模型完成，0 次回退，P50 2.95 秒、P90 5.4 秒；修正 `then` 的兼容处理后不再需要自我纠正。6 个房间同时运行时，有说明的 74 次机器人动作全部由模型决定（之前 41% 由规则机器人代打）。

## 已有接口的兼容验证

2026-10-12，复用配置的 `qwen3.8-flash-next` 接口最初返回 HTTP 200，但输出预算全部用于内部推理，没有最终 JSON。加入该兼容接口支持的 `reasoning_effort=none` 后，真实请求约 528ms 返回合法候选，未触发规则回退。`MONOPOLY_AI_REASONING_EFFORT` 仅在聊天接口配置该字段时发送；本机另设置 `MONOPOLY_AI_DISABLE_THINKING=true`，标准提供者可保留默认关闭。内部推理从不作为游戏提示或日志发布。

有关思考开关的提供者说明：[Alibaba Cloud OpenAI 兼容接口文档](https://www.alibabacloud.com/help/zh/model-studio/qwen-api-via-openai-chat-completions)。实际兼容性以本机真实接口验证为准；原始输出和 API 密钥不进入验收记录。
