# Monopoly 的最优策略与求解器调研

调研日期：2026-10-15。以下区分公开研究的结论、作者对开源项目的说明，以及针对本仓库的工程建议。没有运行第三方项目、复现其胜率或复制其实现。

## 结论

本次找到的是局部概率求解、按对手模型估计胜率的模拟器，以及经验表现较强的规划 / 学习代理；没有找到对包含交易和私有信息的完整标准 Monopoly 给出全局最优策略证明、且可直接接入本游戏的通用求解器。论文或仓库把代理称为 solver，不代表完整博弈已经被数学求解。

随机性本身不妨碍定义最优策略。固定规则、结束条件、收益目标和对手策略后，可以讨论期望收益最优的决策；但“当前净资产最高”“最终获胜概率最大”“团队获胜”不是同一个目标。多人交易、对手反应和未知手牌也需要建模，不能由一张地产收益表决定整盘最优策略。这里的判断是对文献与本仓库规则的归纳。

## 为什么不能直接照搬标准 Monopoly 经验

本仓库采用单颗六面骰、36/44 格和四种地图机制；地图有岔路、渡轮或传送门，角色会改变移动和收益，还有每轮新闻、追赶补贴、私有手牌、持有上限与延后可用规则。结束可以按轮次、时间或目标净资产，团队模式还会改变对手关系。

建设无需先集齐同组，建筑为 0–3 级；净资产按原地价和建筑原价的 75% 等权益计算，成交折扣会改变投资价值。这些规则与标准游戏中的成组建设、房屋供给、双骰和拘留策略明显不同。因此，标准棋盘的热门色组、三栋房子或长期拘留等经验，必须重新在本引擎中评估。

## 现有机器人距离“求解器”有多远

`packages/engine/src/bot.ts` 的三个难度主要由规则、现金储备、落点估值、建设回报和成组交易估值组成，没有搜索完整后续对局或学习出的价值函数。其移动风险估计有简化，不应将困难难度称为最优策略。

服务端 LLM 可以通过 `ai-tools.ts` 的只读工具观察公开资产、风险、路线并预览确定性动作。`preview` 使用实际引擎验证，`look_ahead` 关注近期路线与落点；当前没有 Monte Carlo 胜率估计。工具调用轨迹和理由摘要能解释依据，但不能证明选择最优，也不能替代动作合法性校验。

`scripts/simulate.ts` 已覆盖不同地图、人数、结束方式、拍卖和团队；它用于检查非法动作、引擎不变量及结算一致性。目前同场使用同类规则代理，缺少候选策略的成对比较和置信区间，不能从“300 场全部结束”推出机器人更强。

## 建议的下一步

先做复用本项目纯引擎的有预算 Monte Carlo 动作评估，优先评估买/不买、建设、路线、存款及交易等影响较大的决定；再考虑 MCTS 或学习价值函数。这样能先得到可测量的收益，也能为 LLM 提供数值依据。

1. **公平信息**：输入自己的可见状态，未知手牌和牌堆顺序按合理分布采样；不能读取真实对手私牌、真实未来牌堆或未来随机数。代理可用的观察与评测内部真实状态分开。
2. **可比较的估计**：同一候选集合尽量使用匹配的随机条件，结合不同对手风格、轮换席位和角色，报告胜率估计、置信区间、破产风险与耗时。时间/轮次/团队结束分别评测，使用未参与调参的种子。
3. **服务端预算**：先测每秒模拟量，再定单次预算；放入 worker 或独立进程池，限制并发、内存、深度并支持取消，避免搜索占住 WebSocket 服务的事件循环。
4. **接入 harness**：增加只读评估工具，返回候选、样本数、估计值和风险摘要；LLM 用这些结果做决策说明。缓存与结果绑定 game ID、revision、seat 和 controlEpoch，过时结果丢弃；真正执行时仍由服务端复核并原子持久化。
5. **验收收益**：和当前简单/普通/困难规则代理及现有 LLM 做成对比赛，同时观察胜率、非法动作率、规则兜底率、时延和每局成本。胜率提升是实验结论，不命名为“全局最优”。

这一节是后续方案，本轮没有新增搜索引擎或修改机器人的战略策略。
